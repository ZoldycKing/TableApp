# Работа с проектом

## Подготовка и проверки

Используйте версии Node.js и pnpm из README, выполните `pnpm install --frozen-lockfile`,
создайте `.env`, запустите Docker Compose и примените миграции.
Работайте в отдельной ветке и описывайте конкретное изменение поведения.

```sh
pnpm typecheck
pnpm test
pnpm build
```

Для сборки нужен нелокальный `SITE_URL`. Для проверок с базой нужен
`DATABASE_URL` в окружении терминала и актуальная схема.
Используйте локальную или временную базу для интеграционных проверок.

При изменении авторизации, синхронизации и вложений дополнительно запустите
HTTP-проверки против локального приложения с PostgreSQL и MinIO:

```sh
pnpm --filter @tableapp/web test:auth
pnpm --filter @tableapp/web test:sync-files
pnpm --filter @tableapp/web test:readiness
```

Скрипты используют `SMOKE_BASE_URL`, создают собственные тестовые данные и
убирают их после проверки. Полная последовательность запуска —
в `.github/workflows/ci.yml`.

## Изменения схемы

1. Измените `packages/db/src/schema.ts`.
2. Выполните `pnpm db:generate` и проверьте SQL.
3. Сохраните миграцию, snapshot и журнал миграций вместе с кодом.
4. Проверьте `pnpm db:migrate` и `pnpm db:migrate:verify`.

Уже применённые миграции не переписывают: добавляют новую миграцию.
Перед обновлением существующей базы сделайте резервную копию;
порядок восстановления описан в `docs/backups.md`.

## Границы модулей

`schema` содержит чистые правила и не зависит от веба или базы. `formula` и
`import` зависят от `schema`; сервер и UI находятся в `apps/web`.
Проверки доступа выполняйте на сервере и покрывайте сценариями разных рабочих
пространств, ролей и отзыва прав. Тесты должны проверять результат действия.

## Состав репозитория

Не добавляйте `.env`, ключи провайдеров, ссылки входа, данные пользователей,
выгрузки рабочих баз или резервные копии. Для примеров используйте синтетические
данные. `.env.example` содержит только локальные значения и названия настроек.
Необработанные материалы локального аудита исключены через `.gitignore`.
