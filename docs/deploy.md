# Рабочее окружение: что должно быть настроено

Рабочего окружения у сервиса сейчас нет: всё проверялось на машине
разработчика. Поэтому это не отчёт о настроенном сервере, а список того,
что настраивают до первого публичного запуска. Пункты упорядочены по цене
ошибки: верхние ломают сервис или данные, нижние ломают впечатление.

## Карта публичных адресов

Актуальный список маршрутов показывает `pnpm build`, а индексируемые адреса —
`/sitemap.xml`. Это разные списки. В таблицу сборки попадают
служебные маршруты (`/robots.txt`, `/sitemap.xml`, `/opengraph-image`,
`/icon.svg`), все API (`/api/...`) и весь закрытый контур (`/app`, `/team`,
`/t/[tableId]` и прочее) — им в поиске делать нечего. В карте сайта
перечислены адреса, а не страницы: один шаблон `/solutions/[slug]`
разворачивается в шесть адресов, `/templates/[slug]` — в одиннадцать.
Поэтому 7 постоянных + 6 решений + 11 шаблонов = 24.

Четырнадцать неповторяющихся публичных страниц:

| Страница | Индексируется | Проверено |
| --- | --- | --- |
| `/` | да | 200, canonical, разметка организации |
| `/features` | да | 200, canonical |
| `/how-it-works` | да | 200, canonical |
| `/solutions` | да | 200, canonical |
| `/solutions/[slug]` ×6 | да | 200, canonical у каждого |
| `/templates` | да | 200, canonical |
| `/templates/[slug]` ×11 | да | 200, canonical у каждого |
| `/pricing` | да | 200, canonical |
| `/demo` | да | 200, три роли × два устройства различаются |
| `/login` | нет (`noindex, nofollow, nocache`) | 200 |
| `/legal/offer` | нет (`noindex`) | 200, помечена как проект |
| `/legal/terms` | нет (`noindex`) | 200, помечена как проект |
| `/legal/privacy` | нет (`noindex`) | 200, помечена как проект |
| `/a/[slug]` — приложение клиента | нет (`noindex` на самой странице) | 404 с `noindex` на несуществующем |

Плюс страница «не найдено» (404 с `noindex`) и семь постоянных переездов
со старых адресов (`/shablony`, `/dlya/*`, `/legal/oferta`) — все отвечают
308 и ведут на новые адреса.

## 1. Обязательные переменные

| Переменная | Без неё |
| --- | --- |
| `DATABASE_URL` | приложение не стартует |
| `APP_URL` | ссылки входа могут вести на неверный адрес; задайте URL приложения |
| `SITE_URL` | **сборка падает** — и это правильно |
| `SMTP_URL`, `MAIL_FROM` | коды входа печатаются в консоль сервера, то есть входа нет |
| `S3_*` | вложения некуда класть |

Сессии используют случайные идентификаторы и хранятся в базе; `AUTH_SECRET`
из примера окружения сейчас кодом не используется. Наличие этой переменной
не заменяет HTTPS, серверную проверку сессии и проверку доступа.

Про `SITE_URL` отдельно. По нему строятся канонические ссылки, карта сайта
и `robots.txt`. Канонический адрес с `localhost` поисковик читает буквально
и выбрасывает страницу из выдачи, поэтому сборка с пустым или локальным
значением падает намеренно — лучше на сборке, чем через месяц в поисковой
консоли.

Адрес читается **только на сервере** (`src/lib/site-url.ts`). Переносить его
в клиентский код нельзя: переменные окружения в браузер не попадают, и до
клиента доедет пустое значение. Один раз это уже случилось — проверка
срабатывала в браузере и роняла скрипты всех публичных страниц: разметка
приходила с сервера и выглядела целой, а меню, выпадающие списки и переходы
без перезагрузки не работали. За этим теперь следит тест.

Секретов в клиентской сборке нет: проверено поиском значений всех переменных
в собранных скриптах. Наружу уходит только `NEXT_PUBLIC_METRIKA_ID` — номер
счётчика Метрики, и при пустом значении счётчик не подключается вовсе.

## 2. HTTPS и куки

Все куки ставятся с `httpOnly`, `sameSite=lax` и `secure` в рабочей сборке.
Последнее означает, что **по HTTP вход работать не будет**: браузер не примет
куку. Сертификат — не украшение, а условие работы.

## 3. Прокси перед приложением

Живые обновления идут потоком `text/event-stream` и ломаются о настройки
прокси по умолчанию. Приложение отдаёт то, что нужно (`cache-control:
no-store, no-transform`, `x-accel-buffering: no`, сигнал жизни раз в 25
секунд), но со стороны прокси требуется:

- не буферизовать ответ (`proxy_buffering off` для `/api/live/`);
- не сжимать его;
- тайм-аут чтения больше 25 секунд — иначе прокси будет рвать поток между
  сигналами жизни;
- не ограничивать время жизни соединения минутой.

## 4. Один процесс приложения

Подписчики живых обновлений и счётчик частоты попыток входа живут в памяти
процесса. Это осознанное ограничение, а не недосмотр: поддерживаемая схема
запуска — **один процесс приложения** (см. `docs/architecture.md`). Два
процесса за балансировщиком дадут две беды сразу: правка, сделанная
на одном, не доедет до вкладок, подключённых ко второму, а ограничение
частоты писем станет вдвое мягче. Нужен второй процесс — сначала общая шина,
и это отдельная работа, а не переключатель.

После миграции запустите `pnpm --filter @tableapp/web automations:worker`
как отдельную службу с тем же `DATABASE_URL`. Она проверяет очередь каждые
15 секунд. Расписание и история хранятся в PostgreSQL. Если служба пропустила
несколько дней, при запуске она проверит текущие остатки один раз и продолжит
по обычному расписанию. Для разового прохода добавьте `--once`.

## 5. Резервные копии

Механизм есть и проверен разворачиванием (`docs/backups.md`). Политики нет:
куда класть, как часто, сколько хранить и чем шифровать — решения владельца.
До них копии снимаются руками.

## 6. Ошибки

Отказ на странице показывается своей страницей с предложением повторить,
без текста ошибки: в нём оказываются имена таблиц и куски запросов.
Отдельно обработан отказ самой оболочки (`global-error.tsx`) — со своими
стилями прямо в разметке, потому что таблица стилей могла и не загрузиться.

## 7. Что проверено локально, а что нет

Проверено: отдача всех публичных страниц и их заголовков, карта сайта,
`robots.txt`, переезды, отсутствие горизонтальных переливов на восьми ширинах
от 320 до 1600 пикселей, работа меню и выпадающих списков, различие ролей
в демо, двадцать одновременных потоков живых обновлений в течение минуты,
сто одновременных чтений публичных страниц.

Не проверено, потому что проверять не на чем: поведение за настоящим прокси,
работа по HTTPS с `secure`-куками, отправка почты через настоящего провайдера,
приём платежей настоящим провайдером, восстановление на другой машине.
