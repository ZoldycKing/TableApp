# TableApp

Симбиоз Airtable и Glide: совместная база данных с представлениями, поверх неё —
конструктор мобильных приложений. Спецификация MVP — [docs/mvp-scope.md](docs/mvp-scope.md).

## Маршруты

```
/                маркетинговый сайт: продукт, сценарии, тарифы, вход
/login           вход по ссылке на почту
/app             рабочее пространство (первая таблица или импорт)
/t/<id>          редактор таблицы: представления, грид, поля
/apps            список приложений    /apps/<id> — конструктор экранов
/team            команда и роли
/a/<slug>        опубликованное приложение для конечных пользователей
```

Оформление: тёплая песочная база, приглушённый шалфейный акцент, Manrope для
заголовков и Inter для текста через `next/font`. Токены палитры живут в одном
месте — `src/app/globals.css`, там же правится вся цветовая схема.

## Структура

```
packages/schema    типы полей, представления, определение приложения,
                   движок фильтров, сортировки и группировки, дробные индексы
packages/formula   лексер, парсер, вычислитель формул, граф зависимостей
packages/import    разбор CSV, определение кодировки и типов колонок
packages/db        схема PostgreSQL (Drizzle), сид демо-данных
apps/web           Next.js: редактор базы, конструктор приложений, рантайм
```

Ключевое архитектурное решение: **представление** — один объект, который рендерится
и в редакторе базы (грид, канбан, календарь, галерея), и в приложении (список,
плитка, карточка, форма). Движок фильтрации один на обе половины продукта.

Второе: **поля адресуются по стабильным id**, а не по именам. `rows.data` хранит
`{"fld_7f3a": "..."}`. Переименование поля не трогает данные, формулы и привязки.

## Запуск

```bash
pnpm install
cp .env.example .env
docker compose up -d      # PostgreSQL на 5433, MinIO на 9000
pnpm db:migrate           # схема из версионных миграций
pnpm db:seed              # демо-таблица «Заявки»
pnpm db:seed:relations    # таблица «Позиции», связь, Lookup и Rollup
pnpm db:seed:owner        # поле «Ответственный» для проверки прав на строки
pnpm db:seed:photo        # поле «Фото» в «Позициях» для проверки загрузки файлов
pnpm --filter @tableapp/web dev
```

## Миграции

Схема разворачивается только версионными миграциями из `packages/db/migrations`.
`drizzle-kit push` больше не используется: он молча решает, что сделать с базой,
и на переименованиях требует ответа в консоли, которого в CI взяться неоткуда.

```bash
pnpm db:generate          # после правки packages/db/src/schema.ts
pnpm db:migrate           # накатить неприменённые миграции
```

Сгенерированный SQL читают глазами перед применением: в нём видно, где
удаляется колонка, а где переписываются данные. Применённые миграции
отмечаются в `drizzle.__drizzle_migrations`, повторный запуск безопасен.

Индексы, которые не выражаются схемой Drizzle (GIN по JSONB, частичные),
лежат в `packages/db/sql/indexes.sql` и накатываются отдельно:

```bash
docker exec -i tableapp-postgres psql -U tableapp -d tableapp < packages/db/sql/indexes.sql
```

## Проверки

```bash
pnpm test          # 726 проверок в 55 файлах
pnpm typecheck
```

Часть проверок идёт по настоящей базе — конкурентный импорт и подписка.
Без `DATABASE_URL` они пропускаются, а не падают: на машине без поднятой базы
набор обязан молчать. Данные они заводят свои и за собой убирают.

Рабочая сборка требует `SITE_URL` с настоящим доменом: по нему строятся
канонические ссылки и карта сайта, и `localhost` в них — это страницы,
выпавшие из поиска.

```bash
SITE_URL=https://tableapp.ru pnpm --filter @tableapp/web build
```

## Что уже работает

Сквозной путь: CSV → определение кодировки и типов → предпросмотр с правкой
типов → таблица в PostgreSQL → редактор с правкой ячеек, добавлением
и удалением строк. Правки пишутся через серверные действия с проверкой типа,
пересчётом формул и записью в журнал изменений.

Представления: фильтры с вложенными группами условий, многоуровневая
сортировка и группировка, скрытие полей, поиск. Одна и та же конфигурация
рендерится четырьмя способами — таблица, канбан, календарь, галерея.

Поля: создание, смена типа с преобразованием значений, удаление с проверкой
зависимостей. Формулы с живой проверкой выражения и выводом типа результата,
связи между таблицами, Lookup, Rollup и счётчик связей.

Производные значения (Lookup, Rollup, счётчик, формулы) не хранятся, а
считаются на чтении: иначе правка строки требовала бы каскадного пересчёта
всех строк, которые на неё ссылаются.

Приложения: собираются по таблице одним действием (список, карточка, формы
создания и редактирования), публикуются по ссылке вида /a/<адрес> с манифестом
PWA. Экран списка читает представление базы, поэтому фильтры и сортировка
из редактора действуют и в приложении.

Вход по одноразовой ссылке на почту, без пароля — и для участников команды,
и для пользователей приложений. Первый вход неизвестного адреса заводит
пользователя вместе с воркспейсом. Роли: владелец, редактор, зритель.

Команда: владелец приглашает участников по почте, назначает роли и исключает.
Приглашение заводит пользователя без собственного воркспейса и ведёт его сразу
в тот, куда позвали. Последнего владельца нельзя ни понизить, ни исключить —
иначе воркспейс останется без управления. Пользователь может состоять
в нескольких воркспейсах, активный переключается в строке участника.

Данные привязаны к воркспейсу: каждое серверное действие проверяет, что таблица,
представление или приложение принадлежит воркспейсу вошедшего
(`src/lib/authorize.ts`). Знание чужого идентификатора ничего не открывает.

Вход пользователей приложения — тот же механизм, отдельный контур.

Конструктор экранов: экраны добавляются и удаляются, компоненты добавляются,
переставляются и настраиваются, справа — живой предпросмотр черновика тем же
рантаймом, что показывается пользователям. Публикация делает снимок.

Файлы и изображения: загрузка в S3-совместимое хранилище (в разработке MinIO),
показ в гриде, карточках и приложении. Право на файл выводится из права на
строку, в которой он лежит: файл, не попавший ни в одну ячейку, не отдаётся
никому, а картинка из публичного приложения открыта всем.
Правило «пользователь видит только свои строки» применяется на сервере: чужие
записи не попадают даже в разметку страницы. Чтение и запись используют один
предикат доступа (`src/lib/row-access.ts`), чтобы они не разошлись.

Живые обновления: таблицу, открытую в двух вкладках, не нужно перезагружать —
правка приезжает сама. По каналу едет только факт изменения, данные браузер
перечитывает обычным путём со всеми проверками прав. Пока человек печатает
в ячейке, обновление ждёт. Устройство и границы — `docs/architecture.md`,
раздел «Живые обновления».

Импорт: CSV и книги Excel, в книге можно выбрать несколько листов — каждый
станет своей таблицей или допишется в существующую. Лист, который не читается
целиком (слишком много строк или колонок, формулы без сохранённого значения),
не импортируется вовсе и говорит, почему. Повтор не задваивает данные.

Почта: отправка идёт через SMTP, адрес задаётся в `SMTP_URL`. Без него код
входа печатается в консоль сервера — так проходится разработка. Отправитель
на своём домене и записи SPF/DKIM/DMARC — `docs/mail-setup.md`.

Подписка: тарифы, сроки, история платежей и возврат работают; приём оплаты
включается переменной `PAYMENTS_MODE`. Без неё кнопки честно отвечают, что
оплата не подключена. Порядок подключения — `docs/payments.md`.

Резервные копии: снять и развернуть копию — `pnpm db:backup`, подробности
и то, какие решения нужны от владельца, — `docs/backups.md`. Хранение
технических журналов: `pnpm --filter @tableapp/web retention` показывает,
что накопилось; удаление включается только после согласования сроков
(`docs/legal-todo.md`).

Запуск в рабочем окружении: обязательные переменные, требования к прокси
для живых обновлений и то, что ещё не проверено, — `docs/deploy.md`.
