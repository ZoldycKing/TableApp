# Как устроен TableApp

Описание архитектуры проекта. Текущее состояние исправлений и следующие задачи
собраны в [плане развития](roadmap.md); раздел «Чего нет» в конце описывает
ограничения реализации.

## Каркас

Монорепозиторий на pnpm. Четыре пакета и одно приложение.

```
packages/schema   типы и чистые правила: поля, значения, фильтры,
                  представления, определение приложения, роли, время
packages/formula  формулы и производные поля: разбор, вычисление,
                  Lookup, Rollup, количество связей
packages/import    чтение CSV и XLSX, определение типов колонок
packages/db        таблицы Postgres (Drizzle) и подключение

apps/web           Next.js 16, App Router. Весь интерфейс и весь сервер
```

Зависимости идут в одну сторону: `schema` не знает ни о базе, ни о вебе;
`formula` и `import` знают только `schema`; `db` знает `schema`; `apps/web`
знает всех. Благодаря этому правила прав, фильтров и вычислений проверяются
тестами без базы и без браузера.

## База

Двадцать одна таблица приложения, четыре группы (без служебного журнала миграций).

**Люди и вход**
`users`, `workspaces`, `workspace_members`, `sessions`, `auth_tokens`,
`auth_events`, `staff_sessions`, `app_users`.

**Данные**
`tables`, `fields`, `rows`, `views`, `row_changes`, `mutations`, `attachments`.

**Приложения**
`apps` — определение приложения хранится JSON-документом в двух колонках:
`draft` (что правит владелец) и `published` (что видят люди).

**Учёт и служебные процессы**
`workspace_usage`, `pending_submissions`, `import_runs`, `subscriptions`, `payments`.

### Ключевое решение: данные в JSONB

`rows.data` — это JSONB, ключи в нём — **идентификаторы полей**, а не названия.
Поэтому:

- добавление колонки не выполняет DDL и не блокирует таблицу;
- переименование колонки не трогает ни одной строки;
- формулы и представления ссылаются на поле по id и переживают переименование.

Плата за это — фильтрация и сортировка идут в памяти, а не индексами. На нынешних
объёмах это незаметно, на десятках тысяч строк станет заметно (см. «Чего нет»).

### Производные поля считаются на чтении

Формула, Lookup, Rollup и количество связей **не хранятся**. Они вычисляются
каждый раз в `computeDerivedRow` ([derived.ts](../packages/formula/src/derived.ts)).
Иначе правка строки в одной таблице требовала бы каскадного пересчёта всех
строк, которые на неё ссылаются, — самый надёжный способ получить расходящиеся
данные.

Из этого следует неочевидное: строки **связанной** таблицы тоже надо подавать
с посчитанными формулами, иначе Rollup по формульной колонке суммирует пустоту.
Этим занимается `relatedIndexFrom`.

## Два контура доступа

Это главное разделение всей системы.

| | Участник пространства | Пользователь приложения |
|---|---|---|
| Кто | владелец, редактор, зритель | роли приложения: клиент, сотрудник, ведущий |
| Таблица сессий | `sessions` | `staff_sessions` |
| Что может | менять структуру: таблицы, поля, приложения | работать с данными внутри опубликованного приложения |
| Проверка | `currentMember()` → [authorize.ts](../apps/web/src/lib/authorize.ts) | `currentAppAccess()` → [app-session.ts](../apps/web/src/lib/app-session.ts) |

**«Изменить данные» не даёт «изменить приложение»** — и не флагом, а устройством:
конструктор проверяет членство в пространстве, а у клиента его нет вовсе.
Пройти эту проверку ему нечем.

Сессия сотрудника заводится **на почту, а не на приложение**: право на каждое
приложение пересчитывается при каждом запросе. Убрали адрес из списка — доступ
пропал на следующем же действии, а не когда истечёт сессия.

## Права: цепочка от человека к полю

```
почта из куки
  ↓  roleFor()         — по списку доступа или роль по умолчанию
role_id
  ↓  screensFor()      — какие экраны открыты
экраны
  ↓  canSeePart()      — какие компоненты и блоки открыты
части экрана
  ↓  writableFields()  — какие поля роль вправе записать
  ↓  readableFields()  — какие поля роль вправе прочитать
  ↓  rulesFor()        — какие строки ей принадлежат
```

Всё это — [app-roles.ts](../apps/web/src/lib/app-roles.ts) и
[row-access.ts](../apps/web/src/lib/row-access.ts), оба модуля чистые.

### Роли задаёт владелец

Роль — запись `{id, name, isDefault}` в определении приложения, а не
перечисление в коде. Правила везде работают по `role_id`; сравнений с
«manager» в модулях прав нет.

**Гость ролью не является.** Роль отвечает на вопрос «что человеку можно»,
а у не вошедшего нет ни имени, ни почты, ни строк, которые были бы его.
Он описывается контекстом, а не выдуманной ролью:

```ts
type Visitor = {
  authenticated: boolean
  roleId: RoleId | null   // у не вошедшего — null, а не «роль гостя»
  email: string | null
  company: string
}
```

Сравнений с «guest» в правилах доступа нет; идентификатор остался только
в чтении старых определений. У экрана — три независимых настройки:

```
access: {
  public: boolean,        ← можно открыть без входа
  publicFields: string[], ← что при этом видно: белый список, и только он
  roles: string[],        ← кому из вошедших
  allowDelete: boolean,
}
```

### Три разных вопроса

| | Кто решает | Пусто значит |
|---|---|---|
| **Открыть экран** | `public` / `roles` | закрыто |
| **Прочитать данные** | `publicFields` (не вошедший) или показанные компоненты (вошедший) | ничего не видно |
| **Записать** | `writableFields` из форм | писать нечем |

Открыть — не значит прочитать: публичный экран без белого списка откроется
пустым. Прочитать — не значит записать: публичную форму видно и заполняется,
но права создать строку у не вошедшего нет.

Для не вошедшего набор полей закрыт **всегда**. Состояния «ограничений нет»,
которое есть у вошедшего для таблиц без экранов, у него не существует:
иначе одна забытая галочка выкладывала бы в интернет всю таблицу.

### До каких строк человек вообще может дойти

Один разбор на всех — `rowReach`. Отвечает на вопрос «до какой строки человек
доходит через открытые ему экраны», и отвечает одинаково вошедшему и нет.

| Исход | Когда | Что уходит в браузер |
| --- | --- | --- |
| `gated` | таблицу показывает список или плитка | только строки, прошедшие отбор хотя бы одного такого экрана |
| `ungated` | таблицу показывает лишь карточка или форма | всё, что прошло правила на строки: сузить нечем |
| `none` | ни один открытый экран эту таблицу не показывает | ничего |

Не вошедший `ungated` не получает никогда: доказать, что конкретная строка
разрешена наружу, можно только выборкой, которую владелец назвал сам.
Публичная карточка без публичного списка не показывает ничего. Правила
на строки к не вошедшему не применяются — сравнивать не с чем.

Ответов было два. Не вошедшему выборку задавало представление и применялась
она на сервере; вошедшему отдавались все его строки, а отбор представления
повторял браузер. Второй путь значил, что строка, убранная владельцем
из списка фильтром, всё равно лежала в исходном коде страницы рядом
с показанной.

### Право выводится из экранов, а не хранится отдельно

Нет таблицы «роль × действие». Если роли не открыта ни одна форма создания
с хотя бы одним полем — создавать ей нечем. Одна сущность вместо двух,
и невозможно состояние «в матрице можно, а экрана нет».

### Что значит «скрыть поле»

Поле, которого нет ни в одном доступном роли компоненте, **не приходит
в браузер** — строки чистятся на сервере в `loadRuntimeForApp`. Это не
`display: none`, значение отсутствует в исходном коде страницы.

Блок сводки права на поле **не даёт**. Иначе плитка «сумма по себестоимости»
на экране клиента отправляла бы клиенту себестоимость каждой строки — ровно то,
что скрыть и хотели. Поэтому блоки считаются на сервере, а если роли колонка
не открыта, число не считается вовсе, и владелец видит об этом предупреждение
в конструкторе.

Решает не размер набора, а `restricted`. Пустой набор у показанной таблицы
значит «показывать нечего», а не «показывать всё»: список, которому не задали
ни одной колонки, ничего не выводит — и отправлять по нему строку целиком
нельзя. Граница проходит по другому месту: у таблицы, которую **ни один экран
не показывает построчно**, закрытого набора не существует, подсчёты идут по всем
колонкам, а строки в браузер не уезжают вовсе (`showsRows`).

При включении «Видно без входа» конструктор перечисляет колонки, которые
станут публичными, поимённо — тем же `readableFields`, что отбирает строки
на сервере. Галочка звучит безобидно, а выкладывает наружу то, что владелец
поставил на карточку для себя.

Поля, по которым представление **отбирает и сортирует**, в браузер больше
не уходят: отбор считает сервер и присылает готовый перечень идентификаторов
строк (`RuntimeApp.screens`). Раньше фильтр «себестоимость больше нуля» делал
себестоимость читаемой для каждого, кому открыт такой список.

Поля **поиска** остаются: поиск идёт по уже полученным строкам прямо
на устройстве, и без этих значений искать не по чему.

### Правила на строки

Несколько на таблицу, складываются по «или»: строка видна, если подошло хотя
бы одно правило. Сравнение — с почтой вошедшего или с его организацией
(организация берётся из списка доступа). Так собирается случай «клиент —
юрлицо, заходят трое, заказы общие».

Владелец строки проставляется **сервером** и не меняется правками с устройства.

## Фронтенд: четыре поверхности

### 1. Редактор базы — `/t/[tableId]`

[table-screen.tsx](../apps/web/src/components/table-screen.tsx) и
[grid/](../apps/web/src/components/grid): таблица с закреплённой первой колонкой,
редактор строки карточкой, подсказки (i) у каждого поля
([field-help.ts](../apps/web/src/lib/field-help.ts) — выводятся из реальных
зависимостей, а не из документации).

Представления: таблица, канбан, календарь, галерея
([views/](../apps/web/src/components/views)). Фильтр, сортировка, группировка —
один и тот же движок, что и на сервере ([filter-eval.ts](../packages/schema/src/filter-eval.ts)).

### 2. Конструктор приложений — `/apps/[appId]`

[app-editor.tsx](../apps/web/src/components/builder/app-editor.tsx): слева экраны,
посередине настройки, справа живой предпросмотр **с переключателем ролей** —
отбор идёт той же функцией, что на сервере, поэтому предпросмотр не может
показать больше, чем покажет продукт.

Отдельные редакторы: роли, правила на строки, доступ к экрану, доступ
к компоненту, блоки сводки с предложениями.

У сводки свой конструктор: предложения с уже посчитанными по вашим данным
числами, пустые блоки по видам, отбор тем же построителем условий, что
и в таблицах, дублирование и перестановка, предупреждения о сломанных
ссылках. Рядом с переключателем ролей — переключатель размера места
(компьютер, планшет, телефон); это два независимых вопроса.

### 3. Рантайм приложения — `/a/[slug]`

[app-shell.tsx](../apps/web/src/components/runtime/app-shell.tsx) — оболочка,
[screen-view.tsx](../apps/web/src/components/runtime/screen-view.tsx) — экраны,
[dashboard-view.tsx](../apps/web/src/components/runtime/dashboard-view.tsx) — сводка.

Пять типов экрана: сводка, список, плитки, карточка, форма.
Пять видов блоков сводки: число, список, доска, кнопки, заметка —
они перечислены одним реестром ([blocks.ts](../packages/schema/src/blocks.ts)),
там же заготовки настроек и проверка на сломанные ссылки.

Сводка **ничего не считает в браузере**: итоги приходят готовыми из
`runtime.blocks`. Ширина блока задана числом колонок из двенадцати отдельно
для широкого экрана, планшета и телефона — одно определение на все размеры,
и меряется место, а не окно.

Разметка зависит от **ширины места**, куда вставлено приложение, а не от ширины
окна: одна и та же оболочка работает и в предпросмотре 384 точки, и на мониторе.

### 4. Публичный сайт

Отдельные страницы, а не якоря одной. Раньше сайт был одной длинной главной
с якорями `#vozmozhnosti`, `#tarify`, `#kak` — и в поиске это ровно один адрес,
что бы на нём ни было написано. Якоря остались и работают, но каждая крупная
тема получила свою страницу.

| Адрес | Что там |
| --- | --- |
| `/` | обзор: боль, шаги, возможности, решения, шаблоны, тарифы, вопросы |
| `/features` | возможности по группам: данные, вычисления, приложения, доступ, безопасность |
| `/how-it-works` | путь от файла до ссылки сотруднику, шесть шагов |
| `/solutions` и `/solutions/[slug]` | шесть дел: кабинет клиента, заявки, производство, рабочее приложение, склад, каталог |
| `/templates` и `/templates/[slug]` | каталог шаблонов и что внутри каждого |
| `/pricing` | тарифы из той же конфигурации, по которой работают ограничения |
| `/demo` | настоящее приложение глазами каждой роли |
| `/legal/*` | обработка данных, условия, оферта — пока заготовки и закрыты от индексации |

Страницы **показывают**, а не перечисляют. Общие части экранов продукта —
список, карточка, форма, доска, таблица — собраны в
[screens.tsx](../apps/web/src/components/marketing/screens.tsx); переключаемые
примеры (одни данные в четырёх представлениях, заказ с пересчётом итога,
одни данные глазами трёх ролей) — в
[demos.tsx](../apps/web/src/components/marketing/demos.tsx); у каждого решения
свой экран — [solution-demo.tsx](../apps/web/src/components/marketing/solution-demo.tsx),
и тест не даёт добавить решение без него. Данные в примерах помечены как пример
и взяты из строк-примеров соответствующих шаблонов.

Таблицы на страницах не обрезаются на телефоне: тот же компонент разворачивает
строки в карточки. Правая часть таблицы, спрятанная обрезкой, — это потерянные
данные, а не компактная вёрстка.

Про деньги на сайте написано ровно то, что делает продукт: пробного периода
в коде нет, у всех бесплатный тариф, платные нельзя оплатить. Цены и потолки
берутся из [plans.ts](../packages/schema/src/plans.ts) — второй список с ценами
однажды уже разошёлся с правдой.

Содержимое страниц лежит данными, а не разметкой:
[solutions.ts](../apps/web/src/lib/solutions.ts) для решений, каталог шаблонов —
для шаблонов, [plans.ts](../packages/schema/src/plans.ts) — для тарифов. Есть тесты,
которые не дают сайту обещать шаблон, которого нет, и ссылаться на страницу,
которой нет.

`/templates` — один адрес на двоих: гостю витрина, которую можно найти в поиске,
вошедшему — она же с кнопкой «Взять шаблон». Прежде этих страниц было две,
`/shablony` и `/templates`, с одним и тем же списком: это либо дубль в поиске,
либо расходящиеся описания, и обычно и то и другое.

`/demo` показывает настоящее приложение глазами каждой роли, читая **черновик** —
публиковать его не нужно, и записи в демо не идут. Там же переключатель размера
экрана: рамка становится шириной 1280 или 390 точек, и **тот же** рантайм сам
разворачивает боковое меню или нижние вкладки. Второго приложения для компьютера
нет; роль уходит на сервер и отбирает данные, размер экрана не уходит никуда
([demo-view.ts](../apps/web/src/lib/demo-view.ts)).

### Поиск

Метаданные собирает один помощник — [seo.ts](../apps/web/src/lib/seo.ts): заголовок,
описание, канонический адрес и поля для соцсетей. Списывать это на каждой
странице значит однажды забыть половину и узнать об этом из отчёта поиска.

Три вещи, которые стоят отдельного упоминания:

- **Канонический адрес у каждой страницы свой.** В корневом макете стоял общий
  `canonical: '/'`, и он наследовался вниз — каждая страница сайта просила
  поисковик считать себя копией главной.
- **Закрытые разделы отказывают в индексации сами.** `robots.txt` закрывает
  обход, но не индексацию: адрес, на который кто-то сослался, попадёт в выдачу
  и без обхода. Поэтому у рабочего пространства и у приложений клиентов
  (`/a/[slug]`) стоит `noindex` в самой странице, а `/a/` в `robots.txt`
  намеренно **не** закрыт — иначе поисковик не прочитал бы этот отказ.
- **Карта сайта собирается из тех же списков, что и страницы**
  ([sitemap.ts](../apps/web/src/app/sitemap.ts)). Новый шаблон попадает в неё сам.

Старые адреса переехали постоянным редиректом (308), список —
в [site.ts](../apps/web/src/lib/site.ts): `/dlya/*` → `/solutions/*`,
`/shablony` → `/templates`, `/legal/oferta` → `/legal/offer`. Тест следит,
чтобы старого адреса не осталось живой страницей, а новый существовал.

Публичный адрес сайта — переменная `SITE_URL` (в разработке подставляется
`APP_URL`). Он один на канонические ссылки, карту сайта и `robots.txt`.

## Путь данных

### Чтение

```
loadRuntimeForApp(app, email, role)
  1. visibleScreensFor   — выбросить экраны и блоки, закрытые роли
  2. referencedViews     — какие представления нужны этим экранам
  3. запрос строк        — по разу на таблицу, одним запросом
  4. relatedIndexFrom    — связанные строки с посчитанными формулами
  5. computeDerivedRow   — формулы, Lookup, Rollup
  6. canAccessRow        — выбросить чужие строки
  7. computeDashboards   — посчитать блоки сводки по полным строкам;
                           наружу уходят числа, а не строки
  8. rowReach            — выбросить строки, до которых человеку не дойти
                           ни через один открытый ему экран
  9. applyView           — отбор и порядок каждого списка; в браузер уходит
                           перечень идентификаторов, а не правило
 10. onlyReadable        — выбросить непоказанные поля
  → в браузер уходит ровно то, что человеку положено,
    и готовые числа вместо строк, по которым они посчитаны
```

Порядок менять нельзя, и особенно — место десятого шага. Урезание полей идёт
**последним**, потому что и блоки сводки, и отбор представлений смотрят в том
числе на колонки, которых человеку не покажут: убери значения раньше, и фильтр
«оплачено = нет» не найдёт колонки «Оплачено» и выбросит все строки до одной.

Отбор представления и отбор блока идут **после** прав и могут только сузить
выборку. Своих прав у них нет.

### Запись

Два пути, оба с одинаковыми проверками:

- **Серверные действия** — [runtime-actions.ts](../apps/web/src/app/runtime-actions.ts):
  `allow()` → `permits` → `writableFields` → `stampOwner` → транзакция + запись
  в журнал.
- **Очередь правок** — [api/sync](../apps/web/src/app/api/sync/route.ts): отдельный
  адрес, а не действие, потому что у действия идентификатор привязан к сборке,
  и очередь, пролежавшая офлайн через выкатку, стала бы недействительной.
  Права проверяются **на каждую правку и на каждое поле**, слияние — по значениям,
  а не по часам ([sync-merge.ts](../apps/web/src/lib/sync-merge.ts)).

Каждая запись оставляет след в `row_changes`: автор, что было, что стало.

## Оболочка платформы

Панель слева, работа справа. Верхняя полоса убрана: разделов стало шесть,
и она уже не справлялась — «Использование» не помещалось, название
пространства обрезалось, почта и кнопка выхода отнимали место у навигации.

Список разделов один на все три вида —
[platform-nav.ts](../apps/web/src/lib/platform-nav.ts). Развёрнутая панель,
свёрнутая и выдвижная на телефоне читают оттуда. Три копии означали бы три
расходящиеся навигации: пункт добавили в одну, забыли в двух, и человек
находит раздел только с компьютера.

Панель — **плавающая карточка вне потока страницы**: узкая полоска слева
с отступами от краёв, скруглением, тонкой границей и мягкой тенью.
Разворачивается она **поверх** содержимого.

| Ширина | Панель | Содержимое |
| --- | --- | --- |
| от 768 | полоска 68, разворачивается до 232 поверх | начинается после полоски и её отступов — 92 пикселя |
| до 768 | верхняя полоса с гамбургером и выдвижное меню | во всю ширину |

Главное правило: **раскладка не пересчитывается никогда**. Ни при наведении,
ни при закреплении. Прежде развёрнутая панель занимала колонку, и её открытие
двигало всё справа — таблицу на тысячу строк, конструктор приложений, сводку.
Двести миллисекунд пересчёта на каждое движение мышью к краю экрана — это
дёрганье, которое видно. Теперь двигается только сама панель, а она вне потока.

### Два состояния

Состояний, которые человек выбирает, ровно два, и оба лежат в куке:

- `auto` — полоска, разворачивается по наведению и схлопывается обратно;
- `pinned` — развёрнута постоянно, по-прежнему поверх содержимого.

Временный разворот состоянием не является и не запоминается: это подсказка,
а не выбор. Запомни его — и панель переоткрылась бы человеку, который
её только что свернул.

Прежде состояний было три, и третье называлось «как получится»: на широком
экране развёрнуто, на планшете свёрнуто. Из-за него на рабочем столе панель
по умолчанию отнимала 232 пикселя, а код не мог сказать, что именно увидит
человек, — это решала ширина окна.

Куку читает серверная обёртка
[app-chrome.tsx](../apps/web/src/components/app-chrome.tsx) — **до первого кадра**.
Иначе человек увидел бы, как панель схлопывается уже после появления
страницы. Имя куки живёт там же, где разбор, а не рядом с самой панелью:
панель — клиентский модуль, и Next подменяет **все** его экспорты клиентскими
ссылками. Серверная обёртка получила бы вместо строки объект и не нашла бы
куку вообще — молча, без ошибки.

Старые значения читаются дальше: прежняя развёрнутая (`0`, `wide`) становится
закреплённой, прежняя свёрнутая (`1`, `narrow`) — полоской.

### Как разворачивается

Три способа, и ни один не единственный:

- **наведение** — задержка 140 мс, уход курсора сворачивает через 220 мс.
  Только там, где есть настоящий курсор: `(pointer: fine) and (hover: hover)`.
  На сенсорном экране наведения не существует, и разворачивать по нему значит
  ловить человека на случайном касании;
- **нажатие** на кнопку в полоске — так это работает на планшете, где
  наведения нет. Щелчок мимо сворачивает обратно;
- **переход клавишей** внутрь панели — иначе человек ходит по значкам
  без подписей.

Кнопка называет действие, а не состояние: «Развернуть панель» у полоски,
«Закрепить панель» у развёрнутой, «Открепить панель» у закреплённой.
У развёрнутой она стоит **наверху**, рядом с названием: закрыть панель ищут
там же, где закрывают любое окно. В подвале под почтой её находили не все.

Анимируется только ширина самой панели и подписи — 200 мс. Подписи сжимаются
до нуля вместе с ней (`max-width` и прозрачность разом), а не исчезают рывком:
иначе текст рвётся поперёк движения. Из разметки они при этом не пропадают —
читающим с экрана подпись нужна в любом виде панели.

У свёрнутых значков остаётся системная подсказка. Своей всплывающей здесь
нет намеренно: полоска разворачивается и от наведения, и от перехода
клавишей, и настоящая подпись появляется через 140 мс — подсказка успела бы
мигнуть и смениться панелью. Системная остаётся для устройства, которое
сообщает о себе «курсора нет»: там разворота по наведению не будет.

### Меню рисуются вне панели

Учётная запись стоит у самого низа панели, и меню, открытое вниз внутри неё,
уезжало за нижний край окна: человек видел одну строчку. Панель к тому же
сжимается в полоску и обрезает содержимое по себе — из неё меню не показать никак.

Поэтому оба меню — и учётной записи, и пространства — рисуются в конце
страницы, а положение считается по месту кнопки на экране: учётная запись
открывается вверх, переключатель вниз, и оба переворачиваются сами, если
не помещаются. За края окна меню не уходит.

Пока меню открыто, развёрнутая панель не сворачивается. Человек тянется к пункту,
курсор при этом уходит с панели — и без этого меню исчезало бы у него
из-под руки.

### Подсветка

По началу пути, а не по точному совпадению: `/t/tbl_123` — это «Данные»,
`/apps/app_123/settings` — «Приложения». Из нескольких совпадений выигрывает
самое длинное. Совпадением считается точный путь или путь с косой чертой,
иначе `/apps` подсвечивало бы и `/app`.

Открытый раздел помечен `aria-current="page"`: цвет — не ответ для того,
кто его не видит.

### Чего в списке нет

Безопасность. На той странице только устройства, подтверждение входа
и журнал — всё про учётную запись и ничего про рабочее пространство.
Она в меню пользователя внизу панели, вместе с выходом.

Тарифа, дорожной карты и настроек нет тоже: страниц под них пока
не существует. Пункт, ведущий в пустоту, хуже отсутствующего — человек
нажимает, попадает на ошибку и перестаёт доверять остальному меню.

### Права

Ни один раздел платформы сейчас не закрыт по роли — закрыты отдельные
действия внутри них. Место под пункт, который будет виден только владельцу,
в списке предусмотрено, но это **отражение** прав, а не сами права: страницу
защищает сервер.

## Навигация внутри приложения

Приложение живёт на одном адресе: экраны переключаются в браузере, сервер
об этом не спрашивают. Пока путь лежал только в памяти страницы, «Назад»
уводило с приложения целиком — из карточки заказа сразу на предыдущий сайт.
На телефоне это тот же жест, которым закрывают что угодно.

Теперь каждый переход кладётся в `history.state`, а экран попадает в адрес:
`/a/slug?e=<экран>&r=<запись>`. У домашнего экрана параметров нет — адрес
приложения человек видит и пересылает.

Правило одно: **стрелка «назад» в шапке и кнопка браузера — одно и то же
действие.** Стрелка просит браузер вернуться, состояние восстанавливает
обработчик `popstate`. Иначе у человека было бы два «назад» с расходящейся
памятью.

| Что | Как ведёт себя |
| --- | --- |
| Переход вглубь, смена вкладки | новая запись истории |
| Отбор и поиск в списке | текущая запись переписывается — иначе каждая буква становилась бы шагом назад |
| Открыли присланную ссылку на карточку | под ней в историю кладётся домашний экран: человеку есть куда вернуться |
| «Назад» с первого экрана | уход с приложения, как и должно быть |

Разбор адреса и `history.state` — в [nav-history.ts](../apps/web/src/components/runtime/nav-history.ts),
и он намеренно недоверчивый. В `history.state` пишет и Next, и страница до нас,
и там лежит то, что осталось от прошлой версии приложения в открытой неделю
вкладке. Всё, что оттуда приходит, разбирается с проверкой: не наше или
ссылается на удалённый экран — не трогаем, человек остаётся где стоял.

История включается **явно**, свойством `browserHistory`. Оболочка стоит ещё
в двух местах — в показе на сайте и в предпросмотре конструктора, — и там она
живёт внутри чужой страницы: писать оттуда в историю значит отнять «Назад»
у самой страницы.

## Выгрузка

Два формата и два места, но путь один.

| Кто | Откуда | Что выгружается |
| --- | --- | --- |
| Владелец | таблица, кнопки «Excel» и «CSV» | текущее представление плюс набранный поиск |
| Пользователь приложения | список или плитка | то, что на экране: те же строки, порядок и колонки |

Оба файла собирает **сервер**, хотя у владельца строки уже в браузере. Книгу
Excel иначе не сделать: библиотека тянет узловые модули и в браузерной сборке
оборачивается полифилами ради одной кнопки. А собирать один формат в браузере,
другой на сервере — верный способ получить два файла с разным содержимым
и не суметь объяснить, какой из них правильный. По той же причине оба формата
строятся из одной решётки значений (`buildGrid`).

Выгрузка из приложения идёт через `loadPublishedApp`, а не через собственный
запрос к базе. Отдельный запрос означал бы вторую копию правил доступа,
и однажды она разошлась бы с первой — а расхождение в выгрузке не видно
на экране, его видят в чужом файле. Экран ищется среди тех, что человеку
открыты; чужой идентификатор просто не находится, и отдельной проверки прав
не нужно.

Выгружает только вошедший. Не потому, что посторонний увидел бы лишнее —
увидел бы ровно витрину, которую владелец и открыл. Но «забрать свои данные»
и «скачать чужой каталог одним нажатием» — разные вещи, и второго владелец,
ставя галочку «видно без входа», не выбирал. Заказать с витрины по-прежнему
можно без входа: там человек оставляет своё, а не забирает чужое.

Формат CSV — под русский Excel: точка с запятой вместо запятой и BOM в начале.
Это ровно то, что мы умеем читать при импорте, поэтому выгруженный файл
загружается обратно.

## Живые обновления

Таблицу открыли вдвоём — правка одного появляется у другого сама, без
перезагрузки страницы.

По каналу едет **только факт**: «в таблице N что-то изменилось». Данные
браузер перечитывает обычным путём (`router.refresh()`), то есть теми же
запросами и с теми же проверками прав, что и при первой загрузке. Гонять
правки отдельным каналом значило бы завести вторую копию правил доступа —
и однажды она разошлась бы с первой.

Механизм — SSE, маршрут `GET /api/live/<tableId>`. В `docs/mvp-scope.md`
стоял WebSocket; решение изменено осознанно и записано там же.

| Что | Как |
| --- | --- |
| Кто может подписаться | `authorizeTable(tableId, false)` при открытии потока |
| Отзыв доступа | те же права перепроверяются на каждом сигнале жизни (25 с), поток закрывается |
| Разделение пространств | подписка идёт по идентификатору таблицы, события чужих таблиц в поток не попадают |
| Обрыв связи | `EventSource` переподключается сам; вкладка, вернувшаяся к человеку, перечитывает состояние |
| Несохранённый ввод | пока фокус в поле, обновление откладывается и применяется, когда поле отпустили |
| Поток событий | события склеиваются за 700 мс: вставка двухсот строк не вызывает двести перечитываний |

### Поддерживаемая схема запуска

Подписчики живут в памяти **процесса**, и это ограничение не про число
серверов, а про число процессов приложения.

Сейчас приложение запускается одним процессом: `next start` без кластера,
без PM2 и без второй копии за балансировщиком — в репозитории нет ни того,
ни другого, в `docker-compose.yml` только база, хранилище файлов и почтовый
приёмник. При такой схеме событие, опубликованное запросом, доходит до всех
открытых вкладок: они подписаны в том же процессе.

Что сломается при двух процессах: правка, пришедшая в процесс А, не дойдёт
до вкладок, подписанных в процессе Б. Внешне это выглядит как «у половины
людей таблица не обновляется» — молча и не воспроизводимо.

Поэтому правило простое: **один процесс приложения**. Понадобится второй —
нужна общая шина, и ближе всего `LISTEN/NOTIFY` Postgres: база и так одна,
отдельный сервис заводить не придётся. Делать это заранее, «на будущее»,
не стали: лишняя зависимость стоит дороже, чем строчка в документе.

Конфликт правок разрешается как и раньше: побеждает последняя запись в ячейку.
Нового здесь нет — живые обновления только показывают результат быстрее.
Чего они **не** делают: не показывают, кто сейчас в таблице, и не блокируют
ячейку, которую правит сосед.

## Импорт

Файл нигде не сохраняется. Книга живёт в браузере и уходит на сервер дважды:
на осмотр (`inspectWorkbookAction`) и на чтение выбранных листов
(`readSheetsAction`). Взамен на сервере нет хранилища чужих книг, которое надо
охранять и убирать; расплата — «дочитать оставшиеся листы» работает, только
пока открыт экран импорта.

**Лист — единица всего.** Он читается целиком или не читается вовсе. Раньше
лист сверх потолка молча обрезался: человек получал таблицу, выглядящую
законченной, и узнавал о пропаже строк недели спустя. Теперь `inspectWorkbook`
считает лист до конца и, если он не помещается, возвращает причину с числами,
а строк не отдаёт вообще.

| Что мешает | Что показываем |
| --- | --- |
| Больше 20 000 строк или 200 колонок | сколько нашли и сколько можно |
| Ни одной строки данных | «нет строк данных» — пустых таблиц случайно не создаём |
| Формулы без сохранённого результата | сколько ячеек и первые пять адресов |
| Лист не читается | сообщение разбора |

Формулы не вычисляем. В файле Excel хранит и выражение, и посчитанное
значение; берём значение. Если его нет — а так бывает у книг, собранных чужой
программой, — лист блокируется с просьбой пересчитать и сохранить книгу
в Excel. Ошибка вычисления (`#DIV/0!`) значением считается: она видна и в файле,
и в таблице, поэтому это предупреждение, а не запрет.

`veryHidden` в списке не показывается: такой лист прячут из самого Excel, и это
почти всегда служебная кухня книги. Обычный скрытый лист виден, помечен и сам
не выбирается.

**Повтор не задваивает данные.** Ключ запуска (`import_runs`: пространство,
`runId`, имя листа) вставляется в той же транзакции, что и строки. Второй
запрос с тем же ключом ждёт первого на уникальном индексе, получает «уже есть»
и уходит в откат вместе со всем, что успел записать, — а в ответ отдаёт
результат первого. Так гасится и двойное нажатие, и повтор после потерянного
ответа. Неудачная транзакция уносит и ключ, поэтому повтор после ошибки
разрешён и нужен.

Место в тарифе занимается **до** записи и вне транзакции — как и в остальном
коде: занять его внутри значило бы держать строку счётчика и одновременно
ждать пересчёт, который идёт отдельным соединением. Поэтому место возвращается
руками: и когда второй потолок не пустил, и когда запись не состоялась.

Сводка перед запуском (`lib/import-plan.ts`) считает потолки по всем выбранным
листам сразу — иначе два листа проехали бы, а третий упёрся. Это
не разрешение: права и потолки проверяются заново при записи.

## Учёт расхода

Считается **на пространство целиком**: человек покупает место для своего дела,
а не квоту на каждую таблицу.

| Что | Как считается |
| --- | --- |
| Строки | `rows` через `tables` к пространству, без удалённых в корзину |
| Таблицы | все таблицы пространства |
| Приложения | только с непустым `published`: черновик потолок не расходует |
| Файлы | сумма размеров вложений, на которые ссылается ячейка |
| Пользователи приложений | для статистики; на стоимость не влияют |

Служебные сущности в расход не входят — и не потому, что их кто-то помнит
исключить. Счёт идёт по `rows` через `tables`, а сессии, журнал изменений,
события входа, очередь мутаций и отложенные заявки лежат в своих таблицах
и до этого запроса не доходят.

### Почему снимок, а не инкремент

Строки появляются в шести местах — сетка владельца, вставка пачкой,
офлайн-очередь, импорт, шаблон, запись из приложения — и удаляются в четырёх.
Держать инкремент в каждом значит иметь десять шансов забыть, а разошедшийся
счётчик хуже пересчитанного: он показывает неправду и не жалуется.

Поэтому в [usage.ts](../apps/web/src/lib/usage.ts) одно место знает, **как**
считать, а `workspace_usage` хранит результат. Пересчёт запускается при
открытии страницы расхода, после импорта, после разворачивания шаблона
и кнопкой владельца.

Снимок нужен не для показа — страница считает начисто, — а для будущих
ограничений: далеко от потолка верим снимку и не считаем, близко —
пересчитываем начисто и решаем точно. `usageFor` уже умеет и то, и другое,
но пока его никто не зовёт: ограничений нет.

### Отказ при превышении

Не единый запрет, а градация. Решение принимается в одном месте —
[limits.ts](../apps/web/src/lib/limits.ts), `assertCanIncreaseUsage`, — а по коду
разбросаны только вызовы.

**Блокируется только рост.** Читать, править, удалять и выгружать существующее
можно всегда, даже далеко за потолком. Ничего созданного не выключается —
ни при превышении, ни при понижении тарифа. Пространство может оставаться
над потолком сколько угодно.

| Ресурс | Что запрещается на потолке |
| --- | --- |
| Строки | ручное создание и импорт; записи из приложения идут на резерв |
| Таблицы | создание новой |
| Приложения | публикация следующего; черновики создаются и правятся всегда, повторная публикация уже живого — тоже |
| Файлы | загрузка, если `занято + размер > потолка`; частичных загрузок нет |

### Аварийный резерв строк

`min(max(5% потолка, 50), 1000)` — 100 строк на бесплатном, 1000 на остальных.

Тратится **только** тем, что приходит из опубликованного приложения само:
заказами клиентов и подтверждёнными заявками с витрины. Руками и импортом
его не потратить — иначе это не аварийный запас, а прибавка к тарифу.

Смысл: владелец, у которого кончились строки, не должен узнавать об этом
от потерянного клиента. Его собственный ввод встаёт сразу, а дело продолжает
работать, пока он решает вопрос. Первая же строка сверх потолка делает
пространство превысившим, и страница расхода говорит об этом целой фразой,
а не оттенком полосы. Резерв кончился — встают и заказы.

### Гонка

Проверка и занятие места — **одно действие**:

```sql
update workspace_usage set rows = rows + :need
 where workspace_id = :ws and rows + :need <= :ceiling
returning rows
```

Условие внутри `update`, поэтому Postgres блокирует строку счётчика сам:
второй запрос дожидается первого и видит уже занятое место. Без этого два
одновременных запроса при 1999 из 2000 оба прочитали бы 1999 и оба вставили
строку.

Проверено: двадцать одновременных броней на последнюю свободную строку —
прошла ровно одна, счётчик встал на 2000.

Ноль затронутых строк означает «не поместилось» **или** «снимка ещё нет»
или «он разошёлся с правдой». Разбирать эти случаи незачем: вызывающий
пересчитывает начисто и пробует ещё раз. Так же лечится и расхождение
счётчика — первый же отказ приводит к пересчёту, и человек получает верный
ответ, а не ложный запрет. Внутри транзакции вызывающего бронь откатывается
вместе с ней.

Удаление освобождает место в той же транзакции. Это не обязательно для
правильности — уехавший вверх счётчик чинится отказом, — но без этого
человек, удаливший сотню строк, упирался бы в потолок до ближайшего
пересчёта.

### Отказ говорит числами

Код и подробности, а не текст: `PLAN_ROW_LIMIT`, `PLAN_ROW_GRACE_EXHAUSTED`,
`PLAN_TABLE_LIMIT`, `PLAN_APP_LIMIT`, `PLAN_STORAGE_LIMIT` — и при каждом
тариф, ресурс, занято, потолок, сколько просили, израсходованный резерв
и следующий тариф. Фразу складывает `explain`, журнал получает разбираемую
запись.

Клиенту приложения не говорят ни про тариф, ни про потолок: это чужие дела
и чужие деньги. Он видит то же, что увидел бы при поломке.

### Тарифы

Лежат в [plans.ts](../packages/schema/src/plans.ts) как **конфигурация**. Цены
ориентировочные и меняются одним списком, не трогая ни учёт, ни проверки.

В потолках намеренно нет числа людей: платить за каждого сотрудника — ровно
то, из-за чего малый бизнес уходит от зарубежных сервисов. Таблицы —
защитный потолок, а не предмет торга: брать за них деньги значит наказывать
человека за нормальную структуру базы.

Пороги предупреждений — 70, 85 и 100 процентов.

## Вход

Ссылка из письма и шестизначный код, пароля нет. Код привязан к браузеру,
где начали вход (`challengeId`), хеши вместо самих кодов, ограничение частоты
по адресу и по IP, отсутствие подсказок о существовании адреса. Второй фактор —
TOTP, написан руками и проверен по контрольным векторам RFC 6238.
Журнал входов и список устройств с кнопкой «выйти везде».

Письма уходят через любой SMTP (`SMTP_URL`, `MAIL_FROM`). Без настроек код
печатается в консоль сервера — это режим разработки, а не заглушка.

## Шаблоны

Шаблон — декларация без кода ([templates/defs/](../apps/web/src/lib/templates/defs)):
таблицы, поля с подсказками, представления, строки-примеры. Одиннадцать штук.

`buildTemplate` разворачивает её в записи базы, выпуская новые идентификаторы, —
человек получает **свои** таблицы, а не копию общих. Строки-примеры помечены
`sample`, и отметка снимается, как только строку тронули: «удалить примеры»
удаляет ровно то, что положил шаблон.

«Клиентский портал» дополнительно приносит готовый доступ: витрина и форма
заказа без входа, кабинет клиенту, две сводки — своя клиенту, своя сотрудникам,
и правило «видит только свои строки», без которого приём заказов не работает.

У каждого шаблона есть публичная страница , и всё на ней
выведено из самого описания: таблицы, число колонок, представления, роли
будущего приложения. Второго списка с названиями не существует — разойдись
он с кодом, страница начнёт обещать таблицы, которых в шаблоне нет.

## Производственный учёт

Шаблон, которому одной декларации не хватило: одна операция «сохранить выпуск»
пишет сразу в три таблицы. Общий движок умеет создать одну строку, и делать
ради этого движок производных записей не стали — вместо него одно действие,
которое знает про производство по имени, и настройка `app.production`, которая
говорит ему, что где лежит.

### Модель

Пять таблиц: продукция, материалы, нормы расхода, производство, движение
материалов. Норма — это **строка** (изделие + материал + расход на единицу),
а не колонка: колонки «Пластик», «Клей», «Коробки» означали бы, что добавить
материал можно только правкой структуры таблицы.

Остаток нигде не хранится числом. Он равен начальному плюс сумма движений —
свёртка по связи «Материал → Движения». Поэтому «сколько было на прошлой
неделе» — вопрос к журналу, а не к памяти человека, и поправить остаток
мимо журнала нельзя.

### Три решения, которые продиктовал движок

**Количество со знаком.** Свёртка умеет `через` + `колонку` + `функцию`,
отбора у неё нет. Считать приход и расход разными свёртками не вышло бы —
остаток собирается одной суммой, и списание обязано быть отрицательным.
Заодно новый тип движения не требует правки расчёта.

**Обратную сторону связи ведём сами.** `symmetricFieldId` в схеме объявлен,
но не заполняется нигде. Значит, строку журнала мало создать — её надо
дописать в связь материала, иначе свёртка считает по старому списку
и остаток не двигается. Поэтому ручное движение склада тоже идёт своим
действием: обычная форма записала бы приход, не изменив остаток.

**Названия связей — подстановкой.** Формула видит в связи идентификатор
строки, а не её название: `{Продукт} & " — " & {Произведено}` дало бы
`row_k7z0s4vlm1 — 18500`. Названия приносят колонки-подстановки, и заголовки
строк собираются уже из них. На карточке приложения такая колонка скрыта —
рядом стоит сама связь, и второе такое же поле читается как ошибка.

### Сохранение выпуска

[production-actions.ts](../apps/web/src/app/production-actions.ts), одна транзакция:

```
место под все строки сразу (1 + число материалов)
  → строка выпуска (идентификатор с устройства, повтор не создаёт второй)
  → по строке журнала на каждый материал, количество отрицательное
  → связь материала дописана новыми движениями
  → row_changes на каждую строку
```

Расход считается [одним модулем](../apps/web/src/lib/production.ts) — тем же,
что показывает предпросмотр до сохранения. Формул две быть не может: разойдись
они однажды, человек увидел бы на экране одно, а в журнале другое.

Списания записываются **числами**, а не формулой. Смена нормы не переписывает
прошлое: выпуск, сделанный по норме 0,012, списал 240 кг — это исторический
факт, а не мнение сегодняшнего справочника. Поэтому же сохранённый выпуск
не правится: у формы правки остаётся один комментарий, а ошибку ввода
отменяют целиком.

Место проверяется на всю операцию сразу и **внутри** транзакции: проверить
только строку выпуска значило бы при полном складе получить выпуск без
списаний — то есть молча разошедшийся учёт.

### Удаление не оставляет сирот

Выпуск и его списания — одна запись учёта, разложенная по двум таблицам.
Поэтому движения уходят вместе с выпуском, и делает это
[общий путь удаления строки](../apps/web/src/lib/production-cascade.ts), а не
приложение: строку удаляют и из таблицы, и из приложения, и обе двери ведут
к одному результату. Остаток возвращается к прежнему сам — он посчитан
по движениям, которых больше нет.

### Роли

Две: директор и начальник производства. Умолчание — начальник: роль достаётся
всякому, кого впустили, но отдельно не назвали, и ошибиться здесь безопасно
можно только в одну сторону.

| | Директор | Начальник производства |
| --- | --- | --- |
| Сводка, нормы, ручное движение склада | да | нет |
| Ввод выпуска, выпуски, материалы, журнал | да | да |
| Продукция | правит | только читает |
| Отмена выпуска | да | нет |

Справочник изделий открыт обоим неспроста: подписи связанных строк выдаются
только по таблицам, до которых человек может дойти, — иначе в форме выпуска
не из чего выбирать. Это же проверяет тест: роль, которой показали связь,
обязана иметь доступ к таблице-цели.

Право удалять живёт на экране целиком, поэтому отмена выпуска вынесена
на отдельный экран, закрытый ролью: разреши её на общей карточке — и удалять
смог бы начальник производства.

## Приём заказов от посторонних

Путь ровно один, обходов нет.

```
витрина → заполнил форму → «куда прислать ответ?» → код на почту
  → pending_submissions (значения ждут, прав в них не хранится)
  → ввёл код → сессия и кабинет → пересчёт прав по действующему определению
  → обычная запись: stampOwner → row_changes → кабинет
```

Прямой записи от не вошедшего не осталось нигде: `permits` отказывает ему
всегда, а флаг `legacyAnonymousWrite` удалён вместе со своей миграцией.
Приложения, собранные до разделения гостя и роли, работают по тому же пути:
их «guest» в списке ролей читается как «видно без входа», а запись идёт
через подтверждение.

### Из чего собрано

| Что | Где |
| --- | --- |
| Приём и отсев значений | `draftFromAnonymous` в [pending-submission.ts](../apps/web/src/lib/pending-submission.ts) |
| Хранение до подтверждения | таблица `pending_submissions`, срок 45 минут, ключ — 32 случайных байта |
| Код, срок, счёт попыток, сессия | [auth-challenge.ts](../apps/web/src/lib/auth-challenge.ts) — тот же модуль, что и обычный вход |
| Пересчёт прав после кода | `revalidatePending` |
| Запись строки | `insertRow` в [row-write.ts](../apps/web/src/lib/row-write.ts) — тот же, что у обычной формы |
| Оба шага целиком | [intake-actions.ts](../apps/web/src/app/intake-actions.ts) |

Второго входа здесь нет намеренно: код, его срок, число попыток, привязка
к браузеру и выдача сессии — общие с обычным входом. Разница ровно одна:
к подтверждению приложена отложенная заявка.

Прав в отложенной заявке не хранится тоже намеренно. Пока человек ищет
письмо, владелец мог убрать поле или закрыть форму; берутся только сырые
значения, а что из них можно записать, решается заново после кода.

### Условие, без которого приём не работает

Подтвердивший почту получает роль по умолчанию — и, значит, должен видеть
**свои** строки. Поэтому приём требует, чтобы владелец заранее задал правило
«видит только свои строки» для этой роли в этой таблице (`ownRowsDeclared`).
Пока правила нет, форма видна, но заказ не принимается, и конструктор говорит
об этом владельцу прямо под переключателем «Видно без входа».

Это не придирка. `canAccessRow` без правил пропускает всё — для сотрудника,
которого владелец внёс сам, так и задумано. Для незнакомца это означало бы
выдать ему чужие заказы с телефонами и суммами. Поэтому у пришедшего
с витрины «правил не задано» значит «ничего не видно»: один `enrolled`
в `AccessViewer` и одна ветка в `canAccessRow`, а не отдельная система прав.

### Кто такой «пришедший с витрины»

Обычный пользователь приложения. Роль хранится у него самого
(`app_users.role_id`, `joined_via = 'intake'`), а не в списке доступа: список —
это слова владельца, и дописывать в них самим было бы подлогом. Список всегда
важнее: если владелец внёс этот адрес, действует его запись.

## Хранение журналов

Сервис ведёт четыре технических журнала, которые растут сами и никому
не принадлежат: записи о входах (`auth_events`), применённые правки
из очереди устройств (`mutations`), ключи повторов импорта (`import_runs`)
и сессии с истёкшим сроком (`sessions`). Уборкой занимается
`lib/retention.ts`, снаружи — `pnpm --filter @tableapp/web retention`.

По умолчанию команда **показывает и не удаляет**. Удаление включает флаг
`--run`, и только для категорий с согласованным сроком: `keepDays: null`
означает «решения владельца ещё нет», и уборка такой категории отказывается
работать. Произвольное число там было бы хуже пустоты — оно выглядело бы
как политика. Сроки и решение, которое требуется от владельца, собраны
в `docs/legal-todo.md`.

Четыре предосторожности внутри:

1. Без согласованного срока не удаляется ничего.
2. Граница считается один раз в начале, поэтому долгая уборка не «едет»
   вперёд во времени и не задевает свежие записи.
3. Удаление идёт пачками по `ctid`, а не одним запросом на миллион строк.
4. `pg_try_advisory_lock` отсекает второй запуск — и весь запуск держится
   на одном закреплённом соединении (`sql.reserve()`). Это обязательно:
   замок принадлежит соединению, а запросы раздаются из пула, так что взятый
   на одном соединении замок нельзя снять на другом — он бы остался висеть,
   а следующий запуск, которому досталось то же соединение, получил бы
   «свободно» (замок повторно входим) и пошёл бы удалять вторым.

Платежи, подписки и журнал изменений строк (`row_changes`) в этот механизм
не входят и входить не будут: первое — бухгалтерские документы, второе
отвечает на вопрос «кто и когда это поменял», ради которого журнал и ведут.
Смешивать их с техническим шумом нельзя, поэтому их нет даже как варианта.

## Чего нет

- **Настоящий приём денег** — контур подписки есть и проверен (создание
  платежа, подтверждение, продление, возврат, идемпотентность уведомлений),
  но работает он в проверочном режиме. Настоящий провайдер не подключён:
  нужны ключи магазина и реквизиты, см. `docs/payments.md`
  и `docs/legal-todo.md`.
- **Понижение тарифа** — сменить тариф в интерфейсе нельзя, только в базе.
- **Графики** — сводка считает числа, рисовать их нечем.
- **Перетаскивание блоков мышью** — порядок меняется стрелками.
- **Автоматизации и уведомления** — «когда X → сделать Y» не существует.
- **Офлайн-очередь без интерфейса** — движок и endpoint готовы и покрыты
  тестами, но в интерфейсе не включены и разбора конфликтов нет.
- **Роль колонкой в таблице пользователей** — роли и организации ведутся
  в списке доступа, а не в данных.
- **Поиск по нескольким таблицам**, расписание по часам, переписка внутри
  приложения.
- **Расписание уборки журналов** — механизм есть и проверен, но сроки хранения
  не согласованы, и автоматическое удаление не включено (см. «Хранение
  журналов» выше и `docs/legal-todo.md`).
- **Политика резервных копий** — снять и развернуть копию можно
  (`docs/backups.md`), но куда класть, как часто и чем шифровать — решение
  владельца, а не умолчание кода.

Почта отправляется через любой SMTP: `SMTP_URL` и `MAIL_FROM` в окружении
(см. `.env.example`). Без них код входа печатается в консоль сервера, и весь
сценарий проходится целиком — это режим разработки, а не заглушка.

Что требуется от окружения при запуске — `docs/deploy.md`.
